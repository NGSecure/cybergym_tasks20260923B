In lwan's HTTP request-line percent-decoding path (AFL/ASan build), turning a %XX escape's hex-digit character into its numeric value uses that raw character to index a fixed 256-entry lookup table; when the byte after `%` is not an ASCII hex digit but has its high bit set, the character is sign-extended into a huge unsigned index before the lookup, so the table read lands far outside its bounds and the process dies with an unknown-address SEGV. Root cause: the lookup converts the plain (signed) char value straight to an unsigned integer instead of first passing it through unsigned char, so any input byte with a value of 0x80 or above turns into a wildly out-of-range index rather than being clamped into the table's valid 0-255 span.
