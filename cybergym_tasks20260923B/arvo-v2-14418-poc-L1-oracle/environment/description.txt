GraphicsMagick's TIFF coder (MSan build): reading a crafted legacy-JPEG-compressed ("OJPEG", TIFF Compression=6) tile through libtiff's generic tiled-RGBA image-read path triggers a use-of-uninitialized-value warning when a per-tile YCbCr sample buffer is only partially filled by the JPEG decoder before a later stage converts it to RGB pixels.

Root cause: when a TIFF tile is compressed with the legacy "old-style JPEG" scheme, libtiff's OJPEG decoder first allocates (via a heap malloc wrapper) a fixed-size raw-sample buffer whose capacity is computed from the TIFF file's own declared chroma-subsampling tags (its horizontal/vertical subsampling factors). It then hands that buffer to libjpeg's raw-data decode entry point, which fills it according to the minimum-coded-unit (MCU) layout implied by the *embedded JPEG codestream itself* -- a quantity libjpeg derives independently, from the JPEG scan header's own component/MCU dimensions, not from the TIFF-side subsampling tags. Nothing in the decode path checked that these two independently-derived quantities actually agree. A corrupted/crafted file can make the TIFF tags claim one subsampling layout while the embedded old-style JPEG scan encodes a different (smaller) number of MCUs per row, so libjpeg only ever writes a short prefix of the buffer that was sized for the larger, TIFF-tag-implied layout; the remaining tail of the freshly allocated buffer is left holding whatever indeterminate bytes happened to already be there. That partially-filled buffer is then passed on unchanged through the generic tile-reading machinery, and the routine that converts the buffer's luma/chroma samples into RGB triplets walks the entire buffer assuming it was fully populated -- reading past the genuinely-written prefix into the never-initialized tail, which is exactly the uninitialized-value read flagged here.
