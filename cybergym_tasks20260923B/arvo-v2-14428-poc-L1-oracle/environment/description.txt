wget2's generic string-to-IRI parsing entry point unescapes percent-encoding and a small fixed set of named HTML-style character entities (ampersand, less-than, greater-than, double-quote, and apostrophe) in place, on its own heap-allocated copy of the input string, before doing any further parsing. Root cause: each entity branch is supposed to write the single decoded output character, advance the read cursor past the whole matched entity, and jump back to the top of the scan loop to re-evaluate from the new position. The branch that decodes the apostrophe entity performs the write and the cursor advance but omits the jump back to the loop top, so control instead falls through into the loop's generic "copy current byte and advance" step, which unconditionally dereferences the cursor once more and moves it one further byte. When the apostrophe entity sits at the very end of the string (its cursor lands exactly on the string's own terminating NUL right after the entity is consumed), that extra fallthrough step copies the terminator and pushes the cursor one byte past the end of the heap allocation backing the string; the next loop iteration dereferences that cursor to check for end-of-string, producing a one-byte out-of-bounds heap read. This is strictly a missing-loop-continuation defect, not an allocation-sizing bug: the buffer is never undersized (unescaping only ever shrinks or preserves length), the affected direction is an extra unwanted read exactly one byte past the buffer's end (not a write, and not an integer/size overflow elsewhere), and the dangling cursor is the parser's own read pointer into its input copy, not any output/destination pointer. The fix adds back the missing jump-to-loop-top for that one entity branch, making it behave identically to the other four entity branches that already had it.
